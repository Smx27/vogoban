# TypeScript and JavaScript

Vogoban reads TypeScript and JavaScript into the same repository graph as C#: npm packages, files, modules and imports, declarations, and compiler-resolved calls and type references. It needs no Node.js, no npm and no `node_modules`; the TypeScript compiler ships with Vogoban. This page covers the language layer. Framework features are on the [Angular](angular.md) and [React](react.md) pages, and the frontend→backend link is on the [Frontend](frontend.md) page.

## Why it matters

Module imports and compiler-resolved calls are what connect a route to the function that issues an HTTP request. They also let `impact`, `paths`, `dependencies` and the MetaGraph treat a TypeScript function like any C# method. Because nothing is installed or executed, analysis is safe to run on untrusted repositories.

## What Vogoban detects

### Files and packages

- `.ts`, `.tsx`, `.mts`, `.cts` files are TypeScript; `.js`, `.jsx`, `.mjs`, `.cjs` files are JavaScript.
- Each `package.json` becomes a `Project`, with its dependencies (dev, peer and optional scope recorded) as `PACKAGE_DEPENDS_ON` to external npm `Package` entities. npm, yarn and pnpm workspaces, `pnpm-workspace.yaml`, `lerna.json` and `nx.json` are read. A package name used by two `package.json` files is reported as a diagnostic.
- `tsconfig*.json` / `jsconfig*.json` are read with their `extends` chains (inside the repository only), `paths`, `baseUrl` and project references.
- Build output and vendored bundles are skipped and reported with one `file-skipped` diagnostic per directory: `dist`, `build`, `out`, `coverage`, `.angular`, `.next` and similar directories, `wwwroot/lib`, and `*.min.js`, bundle and chunk files. `node_modules` is never read. Override with `"frontend": { "include": [globs], "exclude": [globs] }` in `vogoban.json`.
- Files whose header says they are generated (NSwag, openapi-generator, swagger-codegen, orval, graphql-codegen, `@generated`, `<auto-generated`, "do not edit", "do not modify this file") are marked `generated`.

### Syntax (always)

Tree-sitter extracts declarations, exports, imports, re-exports, `require`, dynamic `import()` and module references. These facts exist even when semantic analysis is off or fails.

| Construct | Relationship |
| --- | --- |
| `import x from "./y"` | `IMPORTS` |
| `import type { T } from "./y"` | `TYPE_IMPORTS` |
| `import("./y")` | `DYNAMIC_IMPORTS` |
| `require("./y")` | `REQUIRES` |
| `export * from "./y"`, `export { a } from "./y"` | `RE_EXPORTS` |
| exported declarations | `EXPORTS` |
| `/// <reference path>`, `new URL("./x", import.meta.url)`, `require.resolve("./x")` | `REFERENCES_MODULE` |

### Module resolution

Vogoban uses its own resolver, restricted to files discovered in the repository. It resolves, in this order:

1. relative specifiers (`./`, `../`, `/`), probing the exact file, `.js`→`.ts`/`.tsx`/`.mts`/`.cts`/`.d.ts` substitution, the extensions `.ts .tsx .d.ts .mts .cts .js .jsx .mjs .cjs`, and `index.*` files;
2. Node built-ins (`fs`, `node:path`, ...) as built-in packages;
3. tsconfig `paths` (longest matching pattern wins), then `baseUrl`;
4. workspace packages by name (a subpath is probed under the package directory and its `src/`; the package entry is the first of `src/index`, `index`, `src/main`, `lib/index` that exists);
5. anything else becomes an external npm `Package`.

A relative import that leaves the repository root, or that matches no discovered file, stays an unresolved reference with the reason. An import of a package that the owning `package.json` does not declare raises an `undeclared-package-import` diagnostic.

### Semantics

The TypeScript compiler API (TypeScript 6.0.3, bundled) builds one program per npm package. The program sees only the repository's discovered files through a virtual file system. It emits `DECLARES`, `CALLS`, `CONSTRUCTS`, `USES_TYPE`, `REFERENCES`, `INHERITS`, `IMPLEMENTS` (type and member level), `EXTENDS` and `OVERRIDES` with `COMPILER_RESOLVED` evidence. JavaScript is compiled in `allowJs` mode (without `checkJs`), so JavaScript semantics are whatever the compiler can determine statically.

## Example

`web-react/tsconfig.json` maps `@/*` to `src/*`, and a hook imports the API module through the alias:

```json
{ "compilerOptions": { "target": "ES2022", "module": "ESNext", "moduleResolution": "bundler", "jsx": "react-jsx", "strict": true, "baseUrl": ".", "paths": { "@/*": ["src/*"] } }, "include": ["src"] }
```

```ts
// web-react/src/useProduct.ts
import { useEffect, useState } from "react";
import { fetchProduct, type Product } from "@/api";

export function useProduct(id: number) {
  const [product, setProduct] = useState<Product | null>(null);
  useEffect(() => {
    fetchProduct(id).then(setProduct);
  }, [id]);
  return product;
}
```

What Vogoban extracts:

- `File web-react/src/useProduct.ts` -`IMPORTS`-> `File web-react/src/api.ts` (resolved through `paths`, `STRUCTURALLY_RESOLVED`) and -`IMPORTS`-> `Package npm:react` (`DECLARED`).
- `useProduct` -`CALLS`-> `fetchProduct` and -`USES_TYPE`-> `Product` (`COMPILER_RESOLVED`).
- `useProduct` gets `frontendRole: hook` from the React plugin, because it is a `use*` function that calls hooks.

```bash
vogoban show web-react/src/useProduct.ts --kind File
vogoban show useProduct --kind Method
```

## Syntax-only mode

`vogoban analyze <path> --no-semantic` skips the TypeScript program (and Roslyn). The frontend graph then contains syntax-level declarations and module imports only, and a `semantic-disabled` diagnostic says so. There are no calls, no HTTP calls, no routes and no component roles in that mode.

## Limitations

- Types from external packages are unknown, because `node_modules` is never read. Calls through values typed by an external package (for example the result of an untyped generic) are not resolved.
- Workspace package entries are found by the fixed candidates `src/index`, `index`, `src/main`, `lib/index`; `main`, `module` and `exports` in `package.json` are not read.
- `tsconfig` `extends` outside the repository is refused (`tsconfig-extends-missing`). Compiler plugins, `typeRoots` and `types` are ignored.
- JavaScript semantics are limited to what the compiler infers without type annotations; dynamic property access and runtime-built modules are not resolved.
- Symbolic links are not followed. Files outside the repository root are never read.
- A rename or a move of a declaration produces a new identity, as for C# symbols.
