# Analyzing real repositories

This page explains how Vogoban decides what to read in a repository, how to tune that with `vogoban.json`, what .NET package restore and multi-targeting change, how large repositories behave, and which environment variables affect analysis. Use it when the default analysis of your repository misses something or reads something it should not.

## What analysis reads

`vogoban analyze <path>` (and `vogoban graph sync`) works on the Git repository that contains `<path>`. It first resolves the repository root with `git rev-parse --show-toplevel`, then lists files and hands them to the analyzers. No repository code is executed by the analyzers themselves and nothing is downloaded; the one exception, MSBuild evaluation of project files, is covered in [Trust modes](trust-modes.md).

### File discovery rules

| Rule | Behaviour |
|---|---|
| File list | `git ls-files -co --exclude-standard`: tracked files plus untracked files that are not ignored by `.gitignore`. Outside Git, the directory is walked. |
| Always ignored directories | `.git`, `bin`, `obj`, `node_modules`, `.vs`, `.idea`, `.vogoban`, `packages`, `TestResults` (at any depth). |
| Frontend build output | TypeScript/JavaScript under `dist`, `build`, `out`, `coverage`, `.angular`, `.next`, `.nuxt`, `.output`, `.svelte-kit`, `.turbo`, `.cache`, `.parcel-cache`, `.vite`, `storybook-static`, `bower_components`, `jspm_packages`, `.yarn`, `vendor`, `.docusaurus`, `wwwroot/lib`, and any `*.min.js`, `*.bundle.js`, `*.chunk.js` or `*.js.map` file is skipped. One `file-skipped` diagnostic per skipped scope reports the count. `frontend.include` in `vogoban.json` overrides this. |
| Generated code | Still analyzed, but flagged `generated`: C# files named `*.g.cs`, `*.designer.cs`, `*.generated.cs`, `*.AssemblyInfo.cs` or starting with `<auto-generated`, and TS/JS files whose first 1 KiB contains `@generated`, `<auto-generated`, an NSwag/openapi-generator/orval/graphql-codegen banner or "do not edit". |
| Symbolic links | Never followed. A link whose name looks like an analyzable file gets a `file-skipped` diagnostic "symbolic links are not followed". |
| Git submodules | Not analyzed. Each gitlink gets the diagnostic "git submodule not analyzed: its contents are external to this repository's graph (register it as its own repository)". Nested non-submodule Git directories get a similar diagnostic. Register submodules as their own repositories and relate them through the [MetaGraph](../features/metagraph.md). |
| File size | Files larger than `VOGOBAN_MAX_SOURCE_FILE_BYTES` (default 8 MiB = 8388608 bytes) are skipped with `FILE_SKIPPED_RESOURCE_LIMIT`. The Roslyn analyzer applies the same limit to files it reaches through MSBuild evaluation. |
| Unknown file types | Files that are not classified (source, project, solution, configuration, contract, pipeline, infrastructure) are ignored silently. JSON/YAML files without a recognizable name are classified from their first 4 KiB: OpenAPI/Swagger marker, ARM template `$schema`, Kubernetes `apiVersion` + `kind`, or a pipeline that starts with `stages:`, `jobs:`, `steps:` or `extends:`. |

Every skip is recorded as a diagnostic, so nothing disappears silently. Diagnostics appear as counts in `vogoban stats` (the Diagnostics table) and one by one in an export:

```bash
vogoban export --format jsonl --out graph.jsonl
grep '"record":"diagnostic"' graph.jsonl
```

`vogoban diagnostics` does **not** list them: in 0.18.0 it is an alias of `vogoban privacy`. See [Troubleshooting](troubleshooting.md#diagnostics-prints-the-privacy-report).

### Keep the store out of the change set

The default store is `./.vogoban/graph.db` relative to the current directory. When you run Vogoban from the repository root, the store files are untracked changes, and `vogoban graph status` reports `CHANGES_DETECTED` with `.vogoban/graph.db`, `-wal` and `-shm` as added files. The same happens with `bin/` and `obj/` after `dotnet restore`. Either ignore them:

```text
bin/
obj/
.vogoban/
```

or keep the store outside the checkout with `--db <path>` or `VOGOBAN_DB`.

## vogoban.json reference

`vogoban.json` is optional. It lives at the repository root and is read on every analysis and sync. A change to it is a configuration change, so the next `graph sync` runs as a full rebuild with `configuration_changed`.

| Key | Type | Effect | Consumer |
|---|---|---|---|
| `repository.id` | string | Pins the repository identity to `configured:<id>` instead of the normalized `origin` remote URL (or `local:<path>` without a remote). Entity ids derive from this identity, so the same id gives the same entity ids on every machine and clone path. | `pipeline/discovery.ts`, MetaGraph `register` |
| `repository.name` | string | Display name used in tables, impact output and the MetaGraph. Default: last segment of the remote URL, else the directory name. | same |
| `openapi` | string[] | Repository-relative paths that are always treated as OpenAPI/AsyncAPI contract documents, even when their name and first 4 KiB do not identify them. A leading `./` is removed. | discovery, `contracts.openapi` plugin |
| `messaging` | object[] | Custom messaging abstractions (your own event bus). See below. | `dotnet.messaging.configured` plugin |
| `infrastructure.pipelines` | glob[] | YAML files matching these globs are Azure Pipelines definitions (useful for templates that do not start with `stages:`/`jobs:`/`steps:`). | discovery, `infrastructure.azure-pipelines` |
| `infrastructure.helmValues` | path[] | Values files merged, in order, into every Helm release of every chart in the repository: after the chart's default `values.yaml` and before the release-specific values files. A missing file produces a `helm-values-missing` diagnostic. | `infrastructure.helm` |
| `infrastructure.environments` | `{ name: glob[] }` | Assigns infrastructure files to a named environment: a file matching a glob (or under a listed directory) is declared for that environment. | infrastructure plugins (`configuredEnvironment`) |
| `frontend.include` | glob[] | TS/JS paths that are analyzed even though they are build output, bundles or vendored code. | discovery |
| `frontend.exclude` | glob[] | TS/JS/HTML paths that are never analyzed. | discovery |

Validation rules, from `src/pipeline/config.ts`:

- The file must be valid JSON. On a parse error the whole file is ignored and an `error` diagnostic `config-invalid` ("invalid vogoban.json: …") is recorded. A `repository.id` in a broken file is therefore also ignored, which changes the identity; see [Troubleshooting](troubleshooting.md#repository-identity-changes-after-editing-vogobanjson).
- Non-string list entries are dropped silently. Unknown top-level keys are ignored.
- A `messaging` entry without a string `name` is dropped with the diagnostic "messaging entries require a name". `dispatch` is `in-process` only when written exactly so; anything else is `external`.
- `frontend` globs that contain a `node_modules` segment, a `..` segment, or start with `/` are dropped (`node_modules` is never read).

### Messaging abstractions

Each entry describes one in-house bus. Facts from it carry evidence `DECLARED`, and they need semantic (Roslyn) analysis, because publishers and handlers are matched by resolved type names.

| Field | Meaning |
|---|---|
| `name` | Framework name shown in `messages` (for example `contoso-bus`). Required. |
| `dispatch` | `external` (default) or `in-process`. |
| `transport` | Optional `{ "broker", "kind": "topic" \| "queue" \| "exchange" \| "stream", "name" }`; publishers and handlers are linked to this transport. |
| `publishers` | `[{ "type", "methods", "messageArgument" }]`: calls to any of `methods` on the fully qualified `type` (receiver or declaring type) publish the argument at index `messageArgument` (default 0). |
| `handlers` | `[{ "interface" }]`: every implementation of this generic interface (fully qualified, without type arguments) consumes its first type argument. |
| `subscriptions` | `[{ "methods", "messageTypeArgument", "handlerTypeArgument" }]`: generic registration calls such as `bus.Subscribe<TMessage, THandler>()`. |

A published object whose static type is not a concrete contract (for example `object` or an interface) becomes an unresolved reference with the reason, never a guessed message.

### Validated example

This example was analyzed with Vogoban 0.18.0 on a copy of the demo repository `contoso-orders`, with a small custom bus added:

```csharp
namespace Contoso.Orders.Api.Messaging;

public interface IEventBus
{
    Task PublishAsync<T>(T message, CancellationToken cancellationToken = default);
}

public interface IHandle<in T>
{
    Task HandleAsync(T message, CancellationToken cancellationToken);
}

public sealed class ReorderService(IEventBus bus)
{
    public Task ReorderAsync(string orderId, string customerId, IReadOnlyList<OrderLine> lines) =>
        bus.PublishAsync(new OrderSubmitted(orderId, customerId, lines));
}

public sealed class OrderSubmittedAuditHandler : IHandle<OrderSubmitted>
{
    public Task HandleAsync(OrderSubmitted message, CancellationToken cancellationToken) => Task.CompletedTask;
}
```

```json
{

  "openapi": ["contracts/orders-public.yaml"],
  "messaging": [
    {
      "name": "contoso-bus",
      "dispatch": "external",
      "transport": { "broker": "rabbitmq", "kind": "exchange", "name": "orders" },
      "publishers": [{ "type": "Contoso.Orders.Api.Messaging.IEventBus", "methods": ["PublishAsync"], "messageArgument": 0 }],
      "handlers": [{ "interface": "Contoso.Orders.Api.Messaging.IHandle" }]
    }
  ],
  "infrastructure": {
    "pipelines": ["eng/templates/*.yml"],
    "helmValues": ["deploy/shared-values.yaml"],

  },
  "frontend": {
    "include": ["web/legacy/*.min.js"],

  }
}
```

The repository also contains `contracts/orders-public.yaml` (an OpenAPI document whose name does not say so), `eng/templates/build.yml` (a pipeline template that starts with `parameters:`), a Helm chart under `deploy/chart/` whose image comes only from `deploy/shared-values.yaml`, an ingress manifest under `deploy/env/prod/`, and a minified legacy script `web/legacy/orders.min.js`.

## .NET package restore

Vogoban does not run `dotnet restore` during local analysis. It reads the restore output that is already on disk (`obj/project.assets.json`) to find the compile references of each package. Without it, the Roslyn compilation cannot bind package types, and references to them become unresolved with the category `missing-package` (plus `dependent-on-unresolved-type` for everything that depends on them).

Measured on a fresh clone of the demo repository (no `obj/` directories):

```text
unresolved: analyzer-limitation=3 dependent-on-unresolved-type=34 ingress-backend-unresolved=1 missing-package=33 no-matching-operation=1 pipeline-project-unresolved=1 unimplemented-operation=1
```

After `dotnet restore` of each project and a new `vogoban analyze .`:

```text
unresolved: dynamic-transport-name=1 ingress-backend-unresolved=1 no-matching-operation=1 pipeline-project-unresolved=1 unimplemented-operation=1
```

Restore before analysis when you can. `dotnet restore` evaluates the repository's MSBuild files, so on code you do not trust it runs that code; do it only where you would also build the repository. Platform workers restore only when `VOGOBAN_WORKER_DOTNET_RESTORE=1` (see [Enterprise platform](enterprise.md#jobs-and-workers)).

Semantic analysis needs a .NET SDK 8 or later. The analyzer looks for `VOGOBAN_DOTNET`, then `dotnet` on `PATH`, then `~/.dotnet/dotnet`. Without one, analysis still succeeds with syntax-only C# facts and records a `semantic-unavailable` diagnostic; see [Troubleshooting](troubleshooting.md#vogoban-cannot-find-dotnet). `--no-semantic` skips Roslyn on purpose.

## Multi-targeting

A project with `<TargetFrameworks>` is compiled once per framework against the matching reference pack, and the results are merged. A fact present in only some frameworks carries `targetFrameworks`, symbols inside `#if` regions carry `conditions`, and a reference that fails only in some frameworks is unresolved with the category `conditional-compilation`. Each framework needs its own restore output. Details and an example: [.NET analysis](../features/dotnet.md).

## Large repositories

Incremental sync and the fact caches are what keep large repositories practical. All published measurements were taken on one machine and are not capacity statements:

| Scenario | Result | Source |
|---|---|---|
| dotnet/eShop full analysis (683 files, 28 projects, 7,298 entities, 26,210 relationships) | 18.3 s, 500 MB RSS, 76 MB store | [Phase 15 release gate](../release/release-gate-phase15.md) |
| eShop incremental: 1 file / 10 files / leaf project file | 9.9 s / 10.7 s / 5.8 s | same |
| eShop 251-file range touching all projects | 16.6–18.2 s (no benefit over full) | same |
| No-op sync | about 0.5 s | same |
| 6 repositories in one store (replicated eShop/eShopOnContainers copies) | 30,626 entities, 114,817 relationships, 348 MB store; MetaGraph build 2.4 s | same |
| Query latency on that store | `find` 170 ms, `impact` 147 ms, `stats` 674 ms | same |
| 4 concurrent analyses into one store | 25–29 s each, peak 946 MB RSS | same |
| Frontend repositories (35–447 TS/JS files) | cold 1.3–17.4 s, warm 0.5–2.5 s | [Frontend analysis](../features/frontend.md) |
| Azure Functions samples (12 repositories) | cold 2.1–17.1 s, warm 0.5–2.6 s | [Azure analysis](../features/azure.md) |

Capacity beyond these sizes (very large single repositories, hundreds of repositories) was not measured. Measure a representative sample of your own repositories.

Practical levers:

- Use `vogoban graph sync` after the first `analyze`. Narrow changes recompile only the affected projects and their dependents; see [Incremental analysis](../features/incremental-analysis.md).
- Exclude what you do not need: generated clients or bundles through `frontend.exclude`, vendored code through `.gitignore`.
- `VOGOBAN_MAX_SOURCE_FILE_BYTES` bounds memory on pathological files. Lowering it skips more files; every skipped file is a diagnostic.
- Keep one store per CI job or developer. Concurrent writers to one SQLite store wait up to 60 seconds for the write lock.

## Environment variables that affect analysis

| Variable | Default | Effect |
|---|---|---|
| `VOGOBAN_DB` | `./.vogoban/graph.db` | Graph store path (relative to the current directory). `--db` overrides it. |
| `VOGOBAN_DOTNET` | unset | Path to the `dotnet` executable used for Roslyn analysis. |
| `VOGOBAN_MSBUILD_EVALUATION` | on | `0` disables MSBuild evaluation (static project reading). Set implicitly by `--untrusted` and by CI sync without `--trust-repository`. Part of the cache key and of the sync plan. |
| `VOGOBAN_MAX_SOURCE_FILE_BYTES` | `8388608` | Per-file size limit for discovery and the Roslyn analyzer. |
| `VOGOBAN_OFFLINE` | unset | `1` refuses non-loopback AI endpoints (same as `--offline`). Analysis never uses the network either way. |
| `VOGOBAN_POLICIES` | `./vogoban-policies` | Policy files for governance commands. |
| `VOGOBAN_ENTERPRISE` | `./vogoban-enterprise.yaml` | Enterprise metadata for security/ownership commands. |
| `VOGOBAN_CORRELATION_ID`, `VOGOBAN_JOB_ID` | unset | Added to every log line (the platform worker sets them). |
| `VOGOBAN_DEBUG` | unset | `1` prints stack traces for unexpected errors (exit 1). |
| `VOGOBAN_BIN` | `vogoban` | Command written into Git hooks by `hooks install`. |

Log output is controlled by `--log-level debug|info|warn|error` (default `info` for `analyze`, `warn` otherwise) and `--log-json`.

## Limitations

- Static analysis never proves runtime behaviour: reflection, configuration loaded at runtime and values computed at deployment time stay unresolved or partial.
- Submodule contents, symbolic links, ignored files and oversized files are never part of the graph.
- A broken `vogoban.json` is ignored as a whole, including its `repository.id`.
- Analysis does not restore packages; results without restore output have lower semantic precision.
